**Summary**

Matrix calling currently assumes that the homeserver domain (MXID domain) is reachable as a public DNS FQDN. Element clients must contact:
`https://<server_name>/_matrix/client/v3/voip/...`

This breaks calling in deployments where the _server_name_ is not a resolvable public domain, such as internal legacy deployments where the server name is something like:
`server_name: company`
and the actual reachable server is at:
`https://company.example.com`
Element attempts to contact _https://company/…_ and calls fail.
_.well-known_ redirection cannot be used because it must exist on the MXID domain, which is not resolvable.

To address this, I propose that Synapse should be able to advertise an alternative VoIP base URL, and Element clients should automatically use it only if it is provided, preserving backwards compatibility.

No client-side configuration required.

**Problem**
**Real-world scenario**

Some older Synapse installations use a short/internal server_name, e.g.:
`server_name: company`
This worked fine historically, because Element and Matrix features did not strictly require the server_name domain to be publicly resolvable.

However, after calling changes in Element and VoIP improvements, clients must now reach the homeserver directly using its MXID domain for:

- call negotiation endpoints
- VoIP signaling endpoints
- TURN credentials lookups
- fallback ICE server queries
- cross-signing lookup during calls

If the MXID domain is not resolvable over global public DNS, calls break on:

- mobile devices
- laptops
- desktops
- any client not using custom DNS entries
- any user outside the controlled network

Organizations cannot fix this via .well-known because:

- It must exist on the MXID domain
- The MXID domain cannot be registered (e.g. company is not a real domain)
- Users are worldwide and use arbitrary ISP DNS servers

Current situation

- No way to override call base URL from server
- Clients must use homeserver domain
- The only workaround is a full homeserver domain migration, which is extremely disruptive (500+ users, many encrypted rooms, non-federatable rooms, E2EE complications, etc.)

**Proposed Feature**

**Add a Synapse configuration option:**
`voip_base_url: "https://company.example.com"`

**Client behavior (Element):**

1. On startup or when capabilities are fetched, Element checks Synapse’s /versions or /capabilities endpoint for a voip_base_url field.

2. If present:
- Element uses this URL for all call-related operations instead of the raw homeserver domain.

3. If not present:
- Element continues using the current behavior (calls use the homeserver domain).

**Why server-only config?**

- Avoids user confusion
- Avoids per-client configuration drift
- Admins control behavior centrally
- Perfectly backwards compatible
- Matches how TURN configuration is already served from the server to clients

**Benefits**
1. Allows legacy/incorrect _server_name_ deployments to continue functioning
Without forcing an invasive domain migration.

2. Zero client-side configuration
All clients behave correctly automatically.

3. Safe and backwards compatible
If the field is absent, nothing changes.

4. Aligns with existing patterns
- TURN servers are advertised by Synapse and consumed automatically by Element.
- A VoIP override follows the same model.

5. Helps real enterprise deployments

Enterprises often:
- inherit old internal domains,
- cannot rename MXIDs,
- cannot modify global DNS,
- have users in different countries on unmanaged devices.
This feature removes one of the biggest blockers to stable VoIP.

**Request**
Please consider:

1. Adding _voip_base_url_ to Synapse configuration
Stored and exposed via _/capabilities_ or _/versions._

2. Updating Element to check this field
And automatically use it for all VoIP operations.

3. Making the feature optional
So existing behavior remains unchanged when not configured.

**Conclusion**

This feature would restore calling functionality for deployments where the MXID domain is not a globally resolvable FQDN — without requiring a disruptive homeserver domain migration.

It is:
- simple
- optional
- non-breaking
- widely useful
- consistent with existing server-advertised configuration patterns

Thank you for your consideration!
