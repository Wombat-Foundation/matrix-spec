The spec [says](https://spec.matrix.org/unstable/client-server-api/#mroompower_levels):

> The power level required to invite a user to the room, kick a user from the room, ban a user from the room, or redact an event sent by another user, is defined by `invite`, `kick`, `ban`, and `redact`, respectively. Each of these levels defaults to 50 if they are not specified in the `m.room.power_levels event`, or if the room contains no `m.room.power_levels` event.

But Synapse [defaults to 0](https://github.com/matrix-org/synapse/blob/f608e6c8cf48d8d5327c5ac04746f4f7f3992e31/synapse/event_auth.py#L351) for `invite` and has been doing that since forever:

    invite_level = get_named_level(auth_events, "invite", 0)

A few years ago, matrix.org had a problem with invite spam due to this and so the default `invite` power level [was raised in Synapse](https://github.com/matrix-org/synapse/pull/6834) during room creation to solve it, without realizing the divergence from the spec.

Changing it now would lead to many old events prior to that change getting rejected and is thus a no-go. At the same time, some implementations like Conduit do not always set a power level during room creation, leading to those rooms becoming split-brained between Synapse and Conduit.

What are we to do? I propose that we should relax the spec to require PL 0 instead of 50 for `invite` as this has been the de facto situation, bringing Synapse under compliance. Then, if the PL50 requirement for `invite` is still wanted, it can be brought back in a new room version. In the meantime, other implementations should mitigate the problem by always setting the `invite` power level during room creation.
