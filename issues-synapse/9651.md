While working on #9639 and thinking about how certain aspects of it actually work, I have a feeling that entries `destination_rooms` are not properly persisted for what it is supposed to do.

Currently, [`store_destination_rooms_entries`](https://github.com/matrix-org/synapse/blob/fc86c73e2eb08879dbd29c24c170780ba8839668/synapse/storage/databases/main/transactions.py#L307) is called in [`_send_pdu`](https://github.com/matrix-org/synapse/blob/844c9b0aaedc7092ee24ff0100de70fb141ab5fe/synapse/federation/sender/__init__.py#L315), which in effect is called in the [`process_event_queue_for_federation`](https://github.com/matrix-org/synapse/blob/844c9b0aaedc7092ee24ff0100de70fb141ab5fe/synapse/federation/sender/__init__.py#L178) loop on every event that is being batched to be sent.

However, this store happens *before* the events are [distributed](https://github.com/matrix-org/synapse/blob/844c9b0aaedc7092ee24ff0100de70fb141ab5fe/synapse/federation/sender/__init__.py#L347-L348) to the individual [per_destination transmission loops](https://github.com/matrix-org/synapse/blob/026503fa3b90c03996a64be95432e345434b4a82/synapse/federation/sender/per_destination_queue.py#L261), which means it is possible for these loops to encounter that the remote is not available, and so `destination_rooms` will be updated with a stream_id from *unsent events*.

This would cause the [catch-up transmission loop](https://github.com/matrix-org/synapse/blob/026503fa3b90c03996a64be95432e345434b4a82/synapse/federation/sender/per_destination_queue.py#L381) to miss some (or all) events that need to be sent to that destination if the destination is soon retried after the call to `store_destination_rooms_entries`, with events that were "marked" during that call now not being sent to the destination.

My suggestion would be to move the `store_destination_rooms_entries` task (or a simpler version of it) to [`_TransactionQueueManager.__aexit__`](https://github.com/matrix-org/synapse/blob/026503fa3b90c03996a64be95432e345434b4a82/synapse/federation/sender/per_destination_queue.py#L602), where `set_destination_last_successful_stream_ordering` is already called to set the `destinations` table (but not `destination_rooms`), and to do this in a way that it is called *once* per successful sent batch of events (for all rooms).

This would also maybe require the `pending_pdus` list to be sorted based on stream_id (and optionally maybe deduplicated, i.e. an "ordered set"), to ensure that only the latest stream_id per room is persisted to the database, *and* the new `store_destination_rooms_entries` task need to only update the `stream_id`, if `event.stream_id > database_entry.stream_id`.
