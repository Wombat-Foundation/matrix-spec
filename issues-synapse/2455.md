### Description

Since you provide a Debian repository and [there are no other platform instructions than the implicit form of "use the repository"](https://github.com/matrix-org/synapse#debian), I figured synapse would install cleanly through it.
Instead, the configuration is utterly incomplete, with issues like server_name not being set (#1630), the configured tls_dh_params_path not being generated, no signing key being generated, etc.

When I tried to fix all of that manually, there was no documentation to be found.
I have yet to find something as simple as a configuration file reference.

All I found over and over was "run `generate-config`".
The problem with that? Most sources continue that with "in your virtual environment".
No documentation = no idea which virtualenv your package generated.

I found no sign of one, so I just straight up ran `generate-config` in the system-wide Python.

It did generate a config, deviating wildly from what your Debian package had (incompletely) created.

I customized a few settings like pid etc. back to the Debian configuration values, under the assumption that they would be geared towards the rest of the package installation.
iow: The Debian package knows how it installed itself, so if it set the paths like that, it probably had a reason.

I also changed the TLS certificate and key back from the self-signed one to a proper Let's Encrypt generated one.

New error: 

> File /etc/letsencrypt/live/[SERVER]/fullchain.pem config for tls_certificate doesn't exist. Try running again with --generate-config

Again: No useful documentation, no idea what its issue is. The cert is fine. It's right there where I said it is. It's being used by the webserver from right there.

Soooo I assumed massive shittiness in the implementation, in that synapse can't follow symlinks.
Nope.

> File /etc/letsencrypt/archive/[SERVER]/fullchain1.pem config for tls_certificate doesn't exist. Try running again with --generate-config

Hm? Maybe a bug? Maybe it can't take a certificate chain after all?

> File /etc/letsencrypt/archive/[SERVER]/cert1.pem config for tls_certificate doesn't exist. Try running again with --generate-config

It cannot be a misunderstanding of what the option expects, for the autogenerated file is exactly the same: A text file with a PEM-encoded certificate.
Oh well.

So I switched it back to the autogenerated self-signed certificates.
New error: 

> "Could not find a webclient."

`web_client` was False in the debconf-generated configuration, but is True in the `generate-config`-generated one.
This is exactly what I meant earlier: The Debian package probably knows how it set up the system, so overwriting the package-provided configuration with a randomly generated one is an utterly stupid process.
Too bad it's the only one that kinda-sorta-maybe works.

Supposedly the server is running now. Can't test it yet, because now Riot is complaining about rejected CORS requests.
I guess I'm gonna have to investigate *that* now.

Quite frankly: I have installed a number of programs from source before and even the least automated source compilations were less complicated and frustrating than this.
**This is the shittiest apt-based installation I have ever encountered.**

### Steps to reproduce

- Install matrix-synapse from the Debian repository
- Configure server name and reporting through the debconf part of the process, as with all other apt packages

### Expectation

Generating a configuration through the package's provided configuration steps should generate an actually functioning configuration.
A wide array of other server softwares shows that this is possible and *can* be expected, *especially* if there is a debconf step in the installation.

If issues are encountered, there should be an easily discoverable documentation of what configuration options are valid, what they do and how to generate a legal value for them.
Ideally, the installation documentation would also include a section regarding common installation issues and how to fix them, as well as documentation as to how the individual platform default configurations differ from the autogenerated one (e.g. pid location), and what the reasoning behind the difference is (e.g. Debian platform convention).

Error messages should be helpful.

### Reality

Not even the one thing that *is* being gathered by debconf, the server name, is properly written to the configuration. The server fails to start, it's missing practically all configuration.
Generating a configuration through the synapse configuration generation mechanism results in a configuration that differs wildly from the Debian-native one, including incompatible differences like expecting a web client even though the package didn't install one.

I have yet to find installation or configuration file documentation beyond README.md.
matrix-synapse doesn't even seem to have a man page.

The error messages don't even seem to make sense on a technical level, let alone help the user/admin.
