### Description

This is somewhat empirical evidence based upon observations of how synapse behaves on busy systems. 
In a relatively large-scale test, I ensured the disk was busy while running synapse and noticed transactions and requests timing out. Once the disk wasn't being slaughtered by another process synapse bounced to normal behaviour right away. Slaughtering the disk again did cause synapse to fail again.

Reducing logging and repeating the same test did result in less failures, although some were still present while synapse tried to log a large amount of data. Disabling logging completely allowed synapse to perform almost as though the disk wasn't being used (there was still some impact, but nothing unreasonable). 

I haven't done any testing on this front, but I suspect making the logging async to the server operation would allow for some gains when the disk is under high load or is just slow (like a raspberry pi). To avoid out of order log entries, this would probably end up looking like an in-memory buffer (yay! more memory!) which streams to the disk independently of incoming requests. There's possibly even a way to do this in the python libraries already being used, although I'm not too familiar with them and haven't looked into it much.
