So this issue is "i had this problem and i think we can improve the logs to help out the next person". I was attempting to setup worker mode and the tcp replication traffic. I had connected the TCP reader to the HTTP endpoint, which doesn't work, but is presumably an easy mistake to make.

While the above log lines are probably representative of what's happened, once you know what's going on, it would be useful for admins setting up worker mode to have a message about why the connection was closed and by who.

On the other side, all you get is:
```
2019-03-28 17:00:41,439 - twisted - 242 - INFO - - Timing out client: IPv4Address(type='TCP', host='127.0.0.1', port=45930)
```

We can improve logging to help diagnosing this failure a lot, my ideas include:

- when timing out client, report which port it was connected to when we time out (if we saw destination_port=7750 in that timing out client, it's easier to match up). This will also help generally diagnose whether a connection failure is on the federation port or the client-server port or the metrics port or ...
- when connection is dropped by the server, report which client side port it used (if we saw a mention of port 45930 on the client side we could match that up)
- When connection dropped by server, report a more expressive message than "was closed cleanly" - that implied that the correct behaviour occurred, where actually we never got a response.
- when connection is dropped by server, report how much replication was performed (if we saw "0 information replicated" then we wouldn't think this was the expected behaviour)
- Consider improving the replication protocol to send an explicit confirmation of initialization, so after 60s we can explicitly log "did not receive confirmation of replication setup from remote" and we can tell "never connected" from "connected and worked for a while, but failed".
