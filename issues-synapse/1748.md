Matrix.org started blackholing (and then 429ing) many federation /send requests starting around 00:05:26 today.  It looks like these may have been ones sending events to #matrix:matrix.org.  They never recovered until I restarted the server around 14:00.

Looking for federation requests that never returned, the first one to fail is:

```
(venv-synapse)matrix@ldc-prd-matrix-004:~/synapse$ cat homeserver.log | grep PUT-8030225
2017-01-01 00:05:26,411 - synapse.access.http.8080 - 59 - INFO - PUT-8030225 - 27.10.136.51 - 8080 - Received request: PUT /_matrix/federation/v1/send/1483176636529/
2017-01-01 00:05:26,413 - synapse.federation.transport.server - 138 - INFO - PUT-8030225 - Request from catalk.xyz
2017-01-01 00:05:26,413 - synapse.federation.transport.server - 244 - INFO - PUT-8030225 - Received txn 1483176636529 from catalk.xyz. (PDUs: 1, EDUs: 1, failures: 0)
2017-01-01 00:05:27,041 - synapse.state - 310 - INFO - PUT-8030225 - Resolving state for !cURbafjkfsMDVwdRDQ:matrix.org with 2 groups
2017-01-01 00:05:27,052 - synapse.state - 325 - INFO - PUT-8030225 - Resolving conflicted state for '!cURbafjkfsMDVwdRDQ:matrix.org'
```

Superficially, it looks like the request from catalk.xyz took out the linearizer lock for curbaf and never relinquished it, causing the huge failure.  It's unclear what it would have got stuck on, and I can't find the miscreant txn in the `received_transactions` table.

This is closely related to #1733 and #1729 but looks to be a different root cause.

It's worth noting that catalk.xyz was renamed from cntalk.xyz at some point fairly recently, which might be triggering new failure modes.  It's also worth noting that the meltdown on Dec 29(?) featured matrix.org desperately searching for a specific missing event from cntalk.xyz.
