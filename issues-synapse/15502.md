### Description

- If you query `/_matrix/client/v3/sync?since=SYNCTOKEN&timeout=TIMEOUT` (where `SYNCTOKEN` is some sync token and `TIMEOUT` is some timeout) when there isn't any new state, the response's `next_batch` will be identical to `SYNCTOKEN`.
- So, when the client is polling, it will make repeated requests to this same URL until there is new state. (Which is normal/expected behaviour as far as I know)
- Expected behaviour is:
  - If an event is sent to a room after a sync request has been sent, but before the timeout has elapsed
    - THEN, the sync request is responded **with the new events** to fairly soon after the event has sent
  - If an event is sent to a room before a sync request has been sent
    - THEN, as soon as the next sync request is sent, a sync response will be immediate and **will contain the new events**

Whilst this seems to be the most of the time, there's a scenario where it doesn't happen
- timeout=0
- At least one empty sync response has been received for the current sync token (i.e. the sync request referred to in the expected behaviour above comes after at least one empty sync response)

In this scenario, it takes about 2 minutes for the new event to show up in the sync response

Here's a script that recreates the bug (with included example output) https://gist.github.com/swedgwood/3d17193e465871518d499b584c7c574c

There's also a similar sounding issue which was marked as resolved by the author https://github.com/matrix-org/synapse/issues/14713 which they fixed by adjusting the cache time.

I'm not familiar with synapse internals, but I'd hazard to guess that something about timeout=0 changes the way caching works - so when the same sync token is used twice, the previous result is cached for the default cache time of about 2 minutes, which coincides with how long it takes for the event to show up in the sync response. 

### Steps to reproduce

- Set up a new account and join one new room
- In one session, keep syncing, with `timeout=0` until the sync response is empty, and so the response's `next_batch` provides the same sync token that was used in the request.
- Send a message to the room
- Sync again, and notice that the response is still empty, despite the new event
- Keep trying to sync over the next two minutes, and notice that the result keeps being empty, until after the 2 minutes is up, when the sync response finally has the new event

(These steps to reproduce rely on sending a message to a room, but if my caching theory is correct, then I think this should occur with any kind of state change that would cause the sync response to be non-empty)

Also see this script for reproducing this error https://gist.github.com/swedgwood/3d17193e465871518d499b584c7c574c
